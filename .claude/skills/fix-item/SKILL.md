# 修正作業の定型フロー

Cyan-Nook プロジェクトで確立された修正フロー。以下の順に進め、**各承認ポイントでは必ずユーザーの返答を待つ**。

## 1. 説明フェーズ

- 対象コードを実際に読み、問題の構造を確認してから説明する（推測で説明しない）
- ユーザーはベテラン3Dアニメーター（プログラミングは初級〜中級）。専門用語は身近な例えを添えて平易な日本語で説明する
- 修正の方向性まで示し、**「対応をお願いします」等の承認を待ってから実装に入る**
- ユーザーが既に内容を理解して修正を依頼している場合、このフェーズはスキップしてよい

## 2. 実装

- 挙動を変えない最小限の変更を基本とする。挙動が変わる場合はその旨を明示する
- シーン・プレハブの変更は Unity MCP（execute_code / manage_components）で行い、変更後にシーンを保存する
- 新機能・新UIを追加する場合は **unityroom 版（体験版）で封鎖すべきか必ず検討**する（メモリ unityroom-demo-edition 参照。封鎖は UI 非表示+コントローラー側停止の二重防御）

## 3. コンパイル確認

- `refresh_unity`（compile=request）→ `read_console`（error のみ）で確認
- 新規 .cs ファイル追加時はアセット未インポートでエラーが出ることがある → `refresh_unity mode=force scope=all`
- `#if UNITYROOM_BUILD` を触った場合は両ビルド構成でコンパイル確認する（define 切替メニュー使用。**終わったら GitHub 版に戻して File > Save Project まで実行**。忘れると ProjectSettings.asset に define が残る）

## 4. レビュー

- 自明でない変更（1行修正・機械的変更以外）は `unity-csharp-reviewer` エージェントに未コミット diff をレビューさせる
- レビュー依頼には「変更内容の要約」と「重点確認ポイント」を必ず添える
- 指摘は鵜呑みにせず妥当性を判断して反映し、反映結果をユーザーへの報告に含める

## 5. テスト手順の提示

- ユーザーが実施する具体的なテスト手順（何をして、何が起これば OK か）を提示する
- **ユーザーのテスト確認を待つ。確認前にコミットしない**

## 6. コミット

- テスト OK の返答を受けてから、**関連ファイルのみ**を `git add`（パス指定。`git add -A` 禁止）
- 含めないもの: `build/` 成果物、AddressableAssetSettings.asset、ProjectSettings.asset、modern_ceiling_globe.mat、.claude/settings.json（意図した変更でない限り）
- メッセージは日本語。1行目は「何をしたか (カテゴリタグ)」形式（例: `(監査🟡性能)`）、本文に理由と方式を簡潔に
- 末尾に `Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>`
- **プッシュはユーザーが行う。git push しない**

## 7. メモリ更新

- 対応した項目が監査メモ等に記載されている場合、✅+コミットハッシュ+運用注意（今後気を付けるべき点）を追記する
- 修正過程で判明した非自明な事実（ハマりどころ・設計判断）は自動メモリに保存する
- MEMORY.md の索引行も現状に合わせて更新する
